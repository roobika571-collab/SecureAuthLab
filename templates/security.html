Cyber Security Implementation Specifications

An in-depth breakdown of the cryptographic primitives, server-side controls, and session defenses engineered into SecureAuth Lab for Task-2.

IMPLEMENTED & VERIFIED

1. Password Storage: Argon2id (RFC 9106)

Passwords are never stored or logged in plaintext. We utilize Argon2id (winner of the Password Hashing Competition, recommended by OWASP). Argon2id is hybrid data-dependent and data-independent, resisting both side-channel attacks and GPU/ASIC parallel brute-force attacks.

hasher = PasswordHasher(time_cost=2, memory_cost=65536, parallelism=1, hash_len=32, type=Type.ID)
stored_hash = hasher.hash(raw_password)
✔ Memory hardness: 64 MiB required per hash verification.
✔ Password hashes are never sent back in API responses or HTML templates.
✔ Passwords are verified via hasher.verify() with exception handling.
IMPLEMENTED & VERIFIED

2. Generic Auth Errors & Timing Attack Mitigation

When login fails, the response displays a strictly generic message: "Invalid email or password." This prevents account enumeration (identifying whether a victim's email exists on the platform).

Additionally, to defeat timing side-channel attacks, if an entered email does not exist in the database, the server runs verify_dummy_password() against a pre-computed dummy Argon2id hash. This ensures CPU execution duration is statistically indistinguishable between existent and non-existent accounts.

if user:
    authenticated = verify_password(user['password_hash'], password)
else:
    verify_dummy_password(password) # Mitigates timing disparity
IMPLEMENTED & VERIFIED

3. Input Validation & Parameterized Queries

While the client-side JavaScript provides visual guidance for user convenience, all security validation is enforced authoritatively on the server in auth_service.py:

  • Email Normalization: Stripped of leading/trailing spaces and lowercased to prevent duplicate accounts via capitalization variance.
  • Length & Regex Guards: Names restricted to 2-60 letters/spaces; emails verified against RFC-compliant pattern; passwords strictly capped at 128 characters to prevent denial-of-service hash exhaustion.
  • SQL Injection Defense (CWE-89): 100% of SQLite operations use parameterized placeholders (?), never string interpolation.
IMPLEMENTED & VERIFIED

4. Rate Limiting (Flask-Limiter)

Sensitive endpoints are protected against credential stuffing and brute-force attacks via Flask-Limiter:

✔ /login: 5 requests per minute per IP address.
✔ /register: 3 requests per minute per IP address.
✔ Global threshold: 120 requests per hour.
Enterprise Architecture Note: For local development and single-process demonstrations, the in-memory backend (memory://) is used. In production deployments with multiple WSGI workers (e.g., Gunicorn or uWSGI), rate limiting MUST connect to a distributed shared storage backend such as redis:// or memcached:// so limits are shared across workers.
IMPLEMENTED & VERIFIED

5. Session Management & Cookie Attributes

Session cookies are hardened against modern web attacks:

  • HttpOnly = True: JavaScript cannot access document.cookie, preventing session hijacking via Cross-Site Scripting (XSS).
  • SameSite = 'Lax': Protects against Cross-Site Request Forgery (CSRF) in cross-origin navigations.
  • Secure = Configurable: Enabled automatically in HTTPS production; safely toggleable via SESSION_COOKIE_SECURE=False for local HTTP testing.
  • Anti-Session Fixation (CWE-384): Whenever a user logs in, session.clear() is executed before establishing new authentication variables, discarding any pre-existing session ID.
  • No Credential LocalStorage: Passwords, tokens, and sensitive state are NEVER stored in browser localStorage.
IMPLEMENTED & VERIFIED

6. Server-Side Inactivity Expiry & Secure Logout

Sessions are bounded by server-side inactivity validation on every request (default: 20 minutes). If a user remains idle past this window, the backend terminates the session and redirects to /login.

Secure Logout: The /logout endpoint clears server-side session variables, sets cookie expiry to 0, and records the event in the audit log.

Anti-Caching Defense: Responses for protected views inject Cache-Control: no-store, no-cache, must-revalidate, max-age=0 and Pragma: no-cache headers, preventing unauthorized viewing of cached pages via browser Back button after logout.

How Evaluators Can Test These Controls

01

Test Rate Limiting

Submit 6 invalid login attempts within 60 seconds. On the 6th attempt, Flask-Limiter will trigger an HTTP 429 Too Many Requests response.

02

Verify Cookie Security

Open Browser DevTools (F12) → Application/Storage → Cookies. Confirm that the session cookie has HttpOnly and SameSite=Lax checked.

03

Test Logout Invalidation

Log in, click Logout, and then click the browser's Back button. The browser will not show cached dashboard content due to no-store headers.

04

Run Automated Tests

Execute pytest tests/test_auth.py -v in VS Code terminal to run the full automated verification suite covering all 12 security requirements.
